# پنل مستقل حسابداری

این قابلیت داخل پروژه‌های فعلی `Domain`، `ApplicationService.Contract`، `ApplicationService` و `Infrastracture` پیاده شده است. پروژهٔ جدید و DbContext جدید ندارد. پوشهٔ `Accounting` در هر لایه فقط برای دسته‌بندی کلاس‌هاست.

## راه‌اندازی

1. روی دیتابیس فعلی، اسکریپت `docs/sql/2026-11-22-accounting-access-and-audit.sql` را دستی اجرا کنید. این اسکریپت فقط نقش حسابدار، جدول مجوزها و جدول تاریخچه را اضافه می‌کند؛ داده و موجودی مالی را تغییر نمی‌دهد.
2. بک‌اند و فرانت جدید را منتشر کنید. اسکریپت روی دیتابیس توسط عامل اجرا نشده است.
3. ادمین از مدیریت کاربران، کاربر با نقش `Accountant` ایجاد یا تعیین کند. شناسهٔ نقش‌های قبلی تغییر نکرده است.
4. ورود حسابدار به `/dashboard/accountant` هدایت می‌شود. ادمین نیز از حسابداری کلینیک به همین پنل دسترسی دارد.
5. ادمین در «دسترسی حسابداران» مجوزهای موردنیاز را انتخاب کند. دسترسی اولیهٔ حسابدار فقط مشاهدهٔ اطلاعات مالی است؛ تأیید پاداش، وصول، ویرایش و حذف پیش‌فرض مجاز نیستند.

## جریان و معماری

`AccountingController → Command/Query Dispatcher → Handler → Application Service → Repository → DentalContext`

Handlerهای جدید فقط هماهنگی سبک دارند. EF در Repositoryها و بخش Persistence/Audit قرار دارد. عملیات موجود مالی از Commandهای قبلی استفاده می‌کنند؛ منطق وصول قسط، وصول ضمانت و بررسی معرفی به سرویس مشترک منتقل شده و مسیرهای قبلی هم همان سرویس را صدا می‌زنند. پاداش مشاور از adapter همان سرویس نسخه‌دار قبلی استفاده می‌کند؛ نرخ یا محاسبهٔ جدیدی برای حسابدار ساخته نشده است.

## بخش‌ها

- پرونده‌های مالی بیمار و جزئیات، بدهی و پرداخت‌ها.
- چک، سفته، ضمانت و جدول اقساط با فیلتر سررسید.
- درآمد و هزینه، دسته‌بندی هزینه و رسید تراکنش.
- فروش و پاداش منشی، پاداش مشاور و معرفی بیمار.
- کیف پول و گردش منشی و بیمار؛ موجودی محاسباتی مشاور از پاداش‌های تأییدشده.
- خروجی CSV و Excel با فیلترهای فهرست؛ سقف ۱۰۰ هزار ردیف، با درخواست محدودکردن بازه برای گزارش بزرگ‌تر.
- تاریخچهٔ قبل/بعد تغییرهای انجام‌شده از پنل حسابداری با شخص و زمان.

## قواعد مالی

- ارزش درمان، وصول، درآمد کلینیک، فروش و پاداش در شاخص‌های جدا نمایش داده می‌شوند؛ جمع این شاخص‌ها موجودی حساب نیست.
- فیلتر پروندهٔ بیمار بر اساس تاریخ ایجاد است؛ وصول در کارت همان بخش، کل دریافتی پرونده‌های انتخاب‌شده است. درآمد/هزینه بر اساس تاریخ تراکنش و بدهی بر اساس سررسید فیلتر می‌شوند. تاریخ پاداش مشاور تاریخ واجد شرایط‌شدن است. فیلتر کیف پول موجودی جاری اشخاص با آخرین فعالیت در بازه را نشان می‌دهد، نه ماندهٔ تاریخی.
- چک و سفتهٔ ضمانت پرداخت نیستند. چک ضمانت فقط به میزان بدهی سررسیدشده و پس از بررسی اسناد منبع و مانده قابل وصول است.
- پرداخت قسط و تأیید پاداش از ثبت تکراری جلوگیری می‌کنند. پاداش ردشده موجودی را شارژ نمی‌کند.
- پاداش جدید مشاور از snapshot خدمت و نرخ ثبت‌شده استفاده می‌کند. قاعدهٔ ثابت صرفاً fallback سوابق قدیمی است. تأیید حسابدار نیز همان بررسی سرویس قبلی را اجرا می‌کند.
- خدمات و تعداد واحد در ویرایش مالی حسابداری از اطلاعات موجود پرونده حفظ می‌شوند؛ ورود دستی واحد جایگزین چارت نشده است.
- کاهش مبلغ درمان زیر مجموع پرداخت قطعی و اسناد پرداخت/اقساط/بدهی باز رد می‌شود. ضمانت در این جمع قرار نمی‌گیرد.
- تغییر مالی ممکن است hash مالی مورد تأیید قبلی را نامعتبر کند؛ منشی باید مجوز انجام خدمت را دوباره بررسی کند.
- برداشت واقعی، تسویه بانکی و اصلاح دستی موجودی در این نسخه اضافه نشده‌اند.

## مجوز و تاریخچه

مجوزها در `AccountingPermissions` تعریف شده‌اند. کنترل نقش در API و کنترل کاربر فعال/مجوز در Application انجام می‌شود. هویت ثبت‌کننده از توکن گرفته می‌شود، نه از payload. تغییر مجوز فقط برای ادمین فعال مجاز است و در درخواست بعدی اثر دارد.

Audit اطلاعات مالی منتخب را ثبت می‌کند؛ رمز، توکن و فرم پزشکی در آن ذخیره نمی‌شوند. Audit در همان تراکنش نوشتن ذخیره می‌شود و شکست آن باعث rollback عملیات است. شناسهٔ رکوردهای ایجادشده پس از تولید در دیتابیس ثبت می‌شود. این تاریخچه، عملیات جدید انجام‌شده از پنل حسابداری را پوشش می‌دهد؛ برای سوابق قبلی یا همهٔ مسیرهای قدیمی تاریخچهٔ گذشته ساخته نمی‌شود.

## API

پیشوند: `/api/accounting`، نقش‌های مجاز: `Admin,Accountant`.

- `GET access`: مجوزهای کاربر جاری و مجوزهای قابل تنظیم.
- `GET overview`: شاخص‌های مستقل مالی.
- `GET sections/{section}`: فهرست صفحه‌بندی‌شده؛ `page`, `pageSize`, `search`, `status`, `fromDate`, `toDate`, `userId`, `caseId`.
- `GET cases/{id}`: جزئیات مالی موجود بیمار.
- `GET cases/{id}/documents` و `GET cases/{id}/documents/{documentId}`: مدارک مالی.
- `GET transactions/{id}` و `GET transactions/{id}/receipt`: جزئیات و رسید.
- `GET export/{section}?excel=true`: Excel؛ بدون گزینه، CSV.
- `POST operations/{operation}`: `{ targetId, data }`؛ فقط عملیات whitelist شده در executorهای Application قابل اجرا هستند. فیلدهای هویت و شناسه‌های داخلی سمت سرور تعیین می‌شوند.
- `GET accountants` و `PUT accountants/{id}/permissions`: فقط ادمین.

خطاهای اعتبارسنجی ۴۰۰، مجوز ۴۰۳، تعارض هم‌زمانی ۴۰۹ و خطای غیرمنتظره ۵۰۰ با `traceId` پاسخ داده می‌شوند. جزئیات خطای ۵۰۰ در لاگ سرور ثبت می‌شود.

## بررسی

تست‌های جدید: ترجمهٔ SQL فیلتر همهٔ بخش‌ها، کنترل مجوز قبل از نوشتن، پاک‌شدن scope، ثبت اتمیک Audit و rollback، شناسهٔ تولیدشده، پرداخت تکراری، پاداش معرفی و وصول ضمانت. تست‌های مالی قبلی هم باید حفظ شوند.

```powershell
dotnet test DentalDashboard.Consultation.Tests/DentalDashboard.Consultation.Tests.csproj -c Release --filter "FullyQualifiedName!~DentalDashboard.Consultation.Tests.ConsultationTests"
node scripts/validate-accounting-dashboard.mjs
node scripts/validate-consultant-service-rewards.mjs
node scripts/validate-patient-file-completion.mjs
npx ng build --configuration development
```

تست‌های کلاس قدیمی `ConsultationTests` برای اجرا به `CONSULTATION_TEST_SQL` روی SQL Server آزمایشی جدا نیاز دارند. دیتابیس واقعی کلینیک را برای آن تنظیم نکنید. تست SQLite در این تغییر فقط دیتابیس موقت حافظه‌ای برای Audit است و Context تولید را عوض نمی‌کند.
